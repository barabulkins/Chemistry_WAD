## 2. Назначение и цели создания веб-сервиса

### 2.1. Назначение
Веб-сервис предназначен для автоматизации учета химических образцов и связанных с ними аналитических услуг в исследовательской лаборатории, предоставления каталога реактивов с возможностью фильтрации по объёму выделившегося газа, интерактивного просмотра карточек ленты с демонстрационными медиаматериалами (фото и видео испытаний), а также разграниченного управления жизненным циклом образцов (черновик $\rightarrow$ публикация $\rightarrow$ логическое удаление).

### 2.2. Цели разработки
1. Реализация защищенного RESTful API с разделением прав доступа на основе ролевой модели.
2. Внедрение механизма аутентификации на основе **хранения сессий и cookies** для NestJS.
3. Обеспечение безопасного хранения учетных данных пользователей с использованием одностороннего криптографического хэширования с солью (`bcrypt`).
4. Автоматическое заполнение идентификатора автора (`creator_id`) из активной сессии при создании новой услуги/образца.
5. Защита мутирующих методов (создание, редактирование, публикация, удаление, лайки) от неавторизованного доступа (возврат кода `401 Unauthorized`).
6. Формирование интерактивной спецификации API по стандарту OpenAPI (Swagger) с поддержкой cookie-авторизации (`connect.sid`).

## 3. Характеристика объекта автоматизации и сущностей предметной области

### 3.1. Предметная область
Объектом учета выступают химические образцы веществ (услуги аналитической лаборатории), исследуемые на массовую долю примесей и объём выделяющегося в ходе реакций газа (например, разложение известняка, растворение мрамора или травление цинка кислотой). К каждому образцу прикрепляются медиаматериалы испытаний (фотография кристаллической структуры и короткое видео химической реакции).

### 3.2. Жизненный цикл образца
```
                POST /api/samples (multipart)
   [Начало] ──────────────────────────────────────► [DRAFT] (Черновик)
                                                        │
                         ┌──────────────────────────────┤
                         │ PUT /api/samples/publish     │ DELETE /api/samples/:id
                         ▼                              ▼
                  [PUBLISHED] (Опубликован)      [DELETED] (Логически удален)
                         │
                         │ DELETE /api/samples/:id (SQL cursor)
                         ▼
                  [DELETED] (Логически удален)
```

## 4. Требования к веб-сервису

### 4.1. Требования к архитектуре и структуре системы
1. Архитектура системы должна строиться по модульному трехзвенному принципу (Controller — Service — Repository/Data Access Layer).
2. Обмен данными между клиентом и сервером должен осуществляться по протоколам HTTP/HTTPS с использованием формата сериализации JSON и формата `multipart/form-data` для передачи бинарных файлов.
3. Бинарные медиафайлы (изображения и видео) не должны храниться напрямую в реляционной БД. Их хранение должно быть вынесено в S3-совместимое объектное хранилище MinIO. В таблицах БД должны сохраняться прямые валидные HTTP-ссылки на объекты.
4. Имена сохраняемых файлов в бакете MinIO должны генерироваться строго на латинице с добавлением глобально уникального идентификатора (`UUIDv4`), исключая коллизии и проблемы с кодировками.

### 4.2. Ролевая модель и разграничение прав доступа
В системе выделяются две основные категории пользователей:

| Роль | Права и доступные функции |
|---|---|
| **Гость (Неавторизованный пользователь)** | • Доступно **ТОЛЬКО чтение-получение данных через API**.<br>• Просмотр каталога опубликованных образцов с фильтрацией (`GET /api/samples`).<br>• Просмотр ленты образцов (`GET /api/samples/feed`).<br>• Просмотр детальной информации об образце (`GET /api/samples/:id`).<br>• Регистрация новой учетной записи (`POST /api/users/register`).<br>• Вход в систему (`POST /api/users/login`).<br>• *При попытке вызова любых методов создателя возвращается `401 Unauthorized`.* |
| **Создатель (Авторизованный пользователь)** | • Все возможности гостя.<br>• Создание нового черновика услуги с **автозаполнением `creator_id` из сессии** (`POST /api/samples`).<br>• Получение данных своего активного черновика (`GET /api/samples/draft`).<br>• Публикация своего черновика (`PUT /api/samples/publish`).<br>• Логическое удаление **только собственных** образцов через SQL-курсор (`DELETE /api/samples/:id`).<br>• Выставление и снятие отметок «мне нравится» (`POST /api/samples/:id/like`).<br>• Просмотр данных своего профиля (`GET /api/users/me`).<br>• Выход из системы (`POST /api/users/logout`). |

### 4.3. Требования к аутентификации, сессиям и безопасности
1. **Механизм сессий:** Для стека NestJS авторизация должна быть реализована на базе серверных сессий и cookies (`express-session`).
2. **Сессионный cookie:** Сервер генерирует идентификатор сессии и передает его клиенту в HTTP-заголовке `Set-Cookie` с именем `connect.sid`.
3. **Безопасность cookie:** Сессионная кука должна снабжаться атрибутами:
   - `httpOnly: true` (защита от кражи через XSS);
   - `sameSite: 'lax'` (защита от межсайтовой подделки запросов CSRF);
   - Срок жизни сессии: 24 часа.
4. **Хэширование паролей:** Пароли пользователей должны хэшироваться криптостойким алгоритмом `bcrypt` с числом раундов соли не менее 10. Хранение паролей в открытом виде запрещено.
5. **Автозаполнение создателя:** При создании нового образца/услуги идентификатор создателя (`creator_id`) должен извлекаться **строго из сессии текущего авторизованного пользователя** (`req.session.userId`). Передача `creator_id` через тело запроса со стороны клиента запрещена.
6. **Контроль доступа:** Защита методов создателя должна производиться через `SessionAuthGuard`. При отсутствии валидной сессии сервер обязан прерывать выполнение и возвращать `401 Unauthorized` с поясняющим сообщением.

### 4.4. Требования к методам REST API

#### Группа 1: Публичные методы (Гость — чтение)
1. `GET /api/samples`:
   - Назначение: выборка опубликованных образцов (`status = 'published'`).
   - Query-параметры: `gas_volume` (опциональный, фильтр по объёму газа).
   - Расчет динамических признаков:
     - `is_creator: 1` — если создатель образца совпадает с ID пользователя в сессии, `0` — если нет (для гостя всегда `0`).
     - `is_liked: 1` — если текущий пользователь лайкнул образец, `0` — если нет (для гостя всегда `0`).
   - Код ответа: `200 OK`.
2. `GET /api/samples/feed`:
   - Назначение: просмотр образцов по одному в режиме вертикальной ленты.
   - Query-параметры: `id` (текущий ID), `next=true` (следующая запись).
   - Особенность: поддержка закольцовывания (после последнего образца возвращается первый).
   - Код ответа: `200 OK`.
3. `GET /api/samples/:id`:
   - Назначение: просмотр детальных данных опубликованного образца.
   - Коды ответа: `200 OK`, `404 Not Found`.

#### Группа 2: Аутентификация и пользователи
1. `POST /api/users/register`:
   - Входные данные: `username`, `email`, `password`.
   - Бизнес-логика: проверка уникальности email, генерация хэша `bcrypt`, сохранение в БД, автоматическая инициализация сессии.
   - Код ответа: `201 Created` с установкой cookie `connect.sid`.
2. `POST /api/users/login`:
   - Входные данные: `email`, `password`.
   - Бизнес-логика: поиск пользователя по email, проверка пароля через `bcrypt.compare`, сохранение `userId` в сессию, возврат сессионной куки.
   - Коды ответа: `200 OK` (успех), `401 Unauthorized` (неверные данные).
3. `POST /api/users/logout`:
   - Назначение: деавторизация.
   - Бизнес-логика: уничтожение сессии на сервере (`req.session.destroy`), очистка cookie `connect.sid`.
   - Код ответа: `200 OK`.
4. `GET /api/users/me`:
   - Назначение: получение информации о текущем вошедшем пользователе.
   - Защита: требует активной сессии (`SessionAuthGuard`).
   - Коды ответа: `200 OK`, `401 Unauthorized`.

#### Группа 3: Методы создателя (Защищенные)
1. `GET /api/samples/draft`:
   - Назначение: получение активного черновика текущего пользователя (`creator_id = session.userId`, `status = 'draft'`).
   - Коды ответа: `200 OK` (черновик или `null`), `401 Unauthorized`.
2. `POST /api/samples`:
   - Назначение: создание нового черновика образца.
   - Формат запроса: `multipart/form-data` (`title`, `image`, `video`).
   - Бизнес-логика:
     - Проверка обязательности файлов изображения и видео (при отсутствии — `400 Bad Request`).
     - Проверка правила: не более 1 активного черновика на пользователя.
     - Загрузка медиа в MinIO S3.
     - **Автозаполнение:** `creator_id = req.session.userId`.
   - Коды ответа: `201 Created`, `400 Bad Request`, `401 Unauthorized`.
3. `PUT /api/samples/publish`:
   - Назначение: публикация активного черновика создателя.
   - Формат тела: JSON (`title`, `description`, `impurities_percent`, `gas_volume`).
   - Бизнес-логика: перевод статуса в `published`, автоматическая простановка `formation_date = NOW()`.
   - Коды ответа: `200 OK`, `401 Unauthorized`, `404 Not Found`.
4. `DELETE /api/samples/:id`:
   - Назначение: логическое удаление образца (Soft Delete).
   - Бизнес-логика:
     - Разрешено удалять **только образцы текущего создателя** (`creator_id = session.userId`).
     - Выполнение в сырой SQL-транзакции с объявлением курсора:
       ```sql
       DECLARE delete_cursor CURSOR FOR
         SELECT id FROM chemical_samples
         WHERE id = $1 AND creator_id = $2 AND status != 'deleted'
         FOR UPDATE;
       FETCH NEXT FROM delete_cursor;
       UPDATE chemical_samples SET status = 'deleted' WHERE CURRENT OF delete_cursor;
       CLOSE delete_cursor;
       ```
   - Коды ответа: `200 OK`, `401 Unauthorized`, `404 Not Found`.
5. `POST /api/samples/:id/like`:
   - Назначение: добавление/снятие лайка (`value: 1` или `value: 0`).
   - Бизнес-логика: привязка лайка к `session.userId` текущего пользователя.
   - Коды ответа: `200 OK`, `400 Bad Request`, `401 Unauthorized`, `404 Not Found`.

### 4.5. Требования к спецификации Swagger (OpenAPI 3.0)
1. Интерактивная документация Swagger UI должна быть доступна по адресу: `/api/docs` (с автоматическим редиректом с `/docs` и `/swagger`).
2. В Swagger UI должна быть объявлена схема аутентификации `cookieAuth` для куки `connect.sid`.
3. Swagger UI должен быть сконфигурирован с опцией `withCredentials: true`, чтобы после выполнения запроса `POST /api/users/login` браузер автоматически отправлял cookie во всех последующих тестовых запросах интерфейса Swagger.
4. Все методы API должны быть логически сгруппированы с помощью тегов:
   - `Публичные методы (Чтение — без авторизации)`
   - `Аутентификация и пользователи`
   - `Методы создателя (Защищенные — с авторизацией)`
5. Для каждого эндпоинта должны быть указаны описание операции (`@ApiOperation`), структура тела запроса (`@ApiBody`), параметры строки и пути (`@ApiQuery`, `@ApiParam`), а также возможные коды и типы ответов (`@ApiResponse`).

```
  │ image_url TEXT         │        │

  │ impurities_percent DEC │        │
  │ gas_volume INT         │        │

  │ creator_id INT (FK)────┘        │
  └────────────────────────┘        │

  ┌────────────────────────────────────┐
  │            sample_likes            │
  ├────────────────────────────────────┤
  │ id (PK, SERIAL)                    │

  │ sample_id INT (FK -> samples.id)   │
  └────────────────────────────────────┘
```

### 5.2. Описание полей таблиц

#### Таблица `users`
- `id` — целочисленный первичный ключ (автоинкремент).
- `username` — отображаемое имя пользователя (NOT NULL).
- `email` — уникальный адрес электронной почты, логин для входа (NOT NULL, UNIQUE).
- `password` — хэш пароля алгоритма `bcrypt` (NOT NULL).

#### Таблица `chemical_samples`
- `id` — целочисленный первичный ключ (автоинкремент).
- `title` — наименование образца (NOT NULL).
- `description` — подробное описание свойств и условий реакции (NULL).
- `status` — состояние образца: `'draft'` (черновик), `'published'` (опубликован), `'deleted'` (логически удален).
- `image_url` — URL адрес загруженного изображения в MinIO S3 (NOT NULL).
- `video_url` — URL адрес загруженного видеоролика в MinIO S3 (NOT NULL).
- `impurities_percent` — процент массовой доли примесей (DECIMAL(5,2), NULL).
- `gas_volume` — объем выделившегося газа в миллилитрах (INTEGER, NULL).
- `created_at` — системная дата создания черновика (DEFAULT NOW()).
- `formation_date` — системная дата публикации образца (NULL).
- `creator_id` — внешний ключ на создателя (`users.id`).

#### Таблица `sample_likes`
- `id` — первичный ключ (автоинкремент).
- `user_id` — внешний ключ на пользователя (`users.id`).
- `sample_id` — внешний ключ на образец (`chemical_samples.id`).

## 6. Порядок контроля и приемо-сдаточных испытаний

### 6.1. Сценарий демонстрации без авторизации (Гость)
1. Выполнить `GET /api/samples` $\rightarrow$ успешное получение списка published-образцов (`200 OK`). В каждом объекте `is_creator: 0` и `is_liked: 0`.
2. Выполнить `GET /api/samples/feed` $\rightarrow$ успешный просмотр ленты (`200 OK`).
3. Попытаться выполнить `POST /api/samples` без сессии $\rightarrow$ получение ошибки `401 Unauthorized`.
4. Попытаться выполнить `GET /api/samples/draft` без сессии $\rightarrow$ получение ошибки `401 Unauthorized`.
5. Попытаться выполнить `DELETE /api/samples/1` без сессии $\rightarrow$ получение ошибки `401 Unauthorized`.

### 6.2. Сценарий демонстрации аутентификации и сессий
1. Выполнить регистрацию `POST /api/users/register` $\rightarrow$ хэширование пароля через bcrypt, автоматическая установка сессии и cookie `connect.sid`.
2. Выполнить запрос `GET /api/users/me` с сессионным cookie $\rightarrow$ получение профиля (`200 OK`).
3. Выполнить `POST /api/users/logout` $\rightarrow$ сессия уничтожается (`200 OK`).
4. Повторный вызов `GET /api/users/me` $\rightarrow$ `401 Unauthorized`.
5. Выполнить `POST /api/users/login` с неверным паролем $\rightarrow$ `401 Unauthorized`.
6. Выполнить `POST /api/users/login` с корректным паролем $\rightarrow$ `200 OK`, выдача новой валидной сессии `connect.sid`.

### 6.3. Сценарий демонстрации методов создателя
1. Авторизованным пользователем выполнить `POST /api/samples` с файлами `image` и `video` $\rightarrow$ образец сохраняется со статусом `draft`, а поле `creator_id` автоматически заполняется ID текущего вошедшего пользователя (`is_creator: 1`).
2. Выполнить `GET /api/samples/draft` $\rightarrow$ получение только что созданного черновика.
3. Выполнить `PUT /api/samples/publish` $\rightarrow$ смена статуса на `published`, установка `formation_date = NOW()`.
4. Выполнить `POST /api/samples/:id/like` $\rightarrow$ выставление отметки `liked: 1`.
5. Выполнить `DELETE /api/samples/:id` $\rightarrow$ soft delete через курсор `delete_cursor FOR UPDATE`.

### 6.4. Проверка документации Swagger
1. Открыть браузер по адресу `http://localhost:3000/api/docs`.
2. Убедиться в наличии трех групп методов: «Публичные методы», «Аутентификация и пользователи», «Методы создателя».
3. Проверить отображение замка авторизации (`connect.sid`) у защищенных методов.
4. Проверить выполнение запросов прямо из Swagger UI с сохранением и передачей cookies.
